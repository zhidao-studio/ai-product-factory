# 工程版本基线

> 核验日期：2026-08-14
> 复核周期：每 31 天、每次正式发布前，以及主框架宣布新的稳定版本时
> 机器校验：`node scripts/verify-version-baseline.mjs`

## 1. “最新稳定”的项目定义

本项目不把包仓库中的 `latest` 标签机械等同于可用版本。统一采用以下口径：

1. **生产运行时**使用最新 LTS 大版本的最新补丁，例如 JDK 和 Node.js；不把生命周期很短的 Current 版本作为脚手架生产基线。
2. **主框架和主语言编译器**使用官方最新 GA 正式版，不使用 Beta、RC、Canary、Nightly 或 Snapshot。仅当稳定主框架缺少稳定配套实现时，才允许登记一个最小、临时的桥接依赖例外。
3. 当主框架的官方兼容矩阵尚未支持最新 GA 时，使用该框架下的**最新兼容稳定版**，并在本文记录阻断原因和解除条件。
4. 五个前端仍是独立工程，各自保存运行时版本文件、包管理器声明和锁文件；不得通过共享运行时代码来统一版本。
5. “主版本最新”不等于把所有直接、间接依赖无差别升级。普通依赖按安全、兼容和真实需求治理，禁止为了数字整齐破坏主框架支持矩阵。

兼容例外必须具备三个条件：有上游事实依据、当前组合通过真实构建、文档明确解除条件。主框架与主语言本身不允许预发布例外；配套桥接依赖也只能逐项登记。不得用“项目习惯”或“以后再说”作为长期停留旧版的理由。

## 4. 升级流程

1. 先核对官方发布页、支持矩阵和运行时要求，区分 GA、LTS、Current 与预发布版本。
2. 更新本文和机器基线，再修改目标工程自己的 manifest、运行时版本文件与锁文件。
3. 主框架升级必须连同其官方模板、编译器、原生插件或构建器做原子兼容检查，不拆出一个表面更新、实际未生效的版本。
4. 执行 `node scripts/verify-version-baseline.mjs`，确认仓库声明没有漂移。
5. 执行受影响工程的完整验证；只有编译通过不能替代原生运行、登录、主题和生产构建验证。
6. 新稳定版尚不兼容时，只更新本文的核验日期、阻断依据和解除条件，不得强行升级或引入预发布依赖。

## 5. AI 与开发人员规则

- 开始升级前先读本文，再读目标工程 `package.json`、POM、锁文件和官方兼容矩阵。
- 不凭记忆宣称某版本“最新”；时间敏感信息必须重新核验官方来源。
- 不使用 `^`、`~` 或 peer 自动解析来决定主框架实际版本；主框架版本由基线和锁文件共同固定。
- 不跨前端复制 lock、tsconfig、Vite/Umi/Taro 配置；相同版本策略不代表五端合并工程。
- 发现最新版不兼容时，先记录事实和影响，再采用最新兼容稳定组合；禁止静默降级，也禁止为了满足字面版本号破坏可运行性。
