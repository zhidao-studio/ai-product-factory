# AI Product Factory 工程宪章

## Core Principles

### I. 需求先行，需求与方案分离

每项真实业务能力必须先形成 `spec.md`，只回答为什么做、谁使用、在什么场景下做、
遵循哪些业务规则、怎样算验收通过，以及本次不做什么。`spec.md` 不得出现技术选型、
接口路径、表和字段设计、工程目录或实现任务；缺失信息只允许形成会改变业务结果的
待确认问题，不得把技术问卷交给需求提出者。需求未被用户明确确认前，禁止进入工程计划。

### II. 事实有来源，禁止自由发挥

AI 和开发者必须先查明当前实现，再提出方案。现有接口、字段、模块、运行方式和完成度
必须来自权威文件或真实代码；不得根据页面、命名习惯、通用脚手架经验或未来设想发明
路径、字段、工程和业务。发现需求与当前事实冲突时必须显式说明并等待决策，不得通过
修改说明文档为偏离现状的实现背书。

### III. 所有权与既有工程模式不可跨越

方案和实现必须保持 Admin、Client、Common 与五个前端的既有所有权，遵循仓库已经采用的
分层、契约、认证、数据和设计系统约束。新能力必须落入最接近的真实模块；没有已确认
消费者和实现的 API、UM、微服务、公共包或抽象层不得提前创建。任何偏离都必须在
`plan.md` 中给出需求依据、影响和更简单方案不成立的原因，并获得用户明确确认。

### IV. 从需求到证据必须可追踪

每个用户场景使用 `US-xxx`，每条业务规则使用 `BR-xxx`，每条验收标准使用 `AC-xxx`。
`plan.md` 必须逐项说明这些编号对工程的影响；`tasks.md` 中每个业务实现任务必须追踪到
至少一个用户场景和相关验收标准，并写明真实文件路径。验证结果必须能回指验收标准，
不得用“已修改”“功能正常”或编译通过代替业务验收证据。

### V. 小步、真实、可验证

只实现已确认范围内的最小完整业务切片，优先复用现有能力。计划中的研究、数据模型、
契约和快速验证说明等附属工件只有在确有内容时才创建，禁止空文件和模板空壳。
验证必须与风险相称，至少覆盖受影响构建、真实契约、关键业务路径和回归边界；失败、
未验证项和环境限制必须如实记录，禁止把未运行的检查描述为通过。

## Spec Kit Artifact Contract

- `spec.md` 是业务需求真相：只包含背景与目标、使用者与场景、业务规则、验收标准、
  范围与非目标、待确认问题。它不得因为实现方便而改变业务含义。
- `checklists/requirements.md` 是需求质量审查，不是实现进度表；只有审查者确认满足时才勾选。
- `plan.md` 是已确认需求的工程翻译：基于当前代码说明影响范围、契约、数据、UI、兼容性、
  安全与验证，并列出允许修改和明确禁止修改的边界。不存在的影响必须写“不涉及”，
  不得制造附属工件凑齐目录。
- `tasks.md` 是已确认计划的执行清单：按用户场景组织，写出依赖、精确路径、交付结果和
  验证方式；不得保留通用初始化、示例任务或与本需求无关的重构。
- `research.md`、`data-model.md`、`contracts/`、`quickstart.md` 仅在对应问题真实存在时生成；
  其结论必须有代码、官方资料或用户决策作为依据。
- `specs/` 只存放用户提出的真实需求，禁止为展示流程创建虚构 Feature Spec。

## Gated Delivery Workflow

1. 使用 `$speckit-specify` 形成需求草稿；仅在业务结果确实不明确时使用
   `$speckit-clarify`，且问题必须少而关键，不得询问实现偏好。
2. 需求结构校验通过且待确认问题关闭后，由用户明确确认 `spec.md`；确认需求不等于授权规划
   或实现。确认后才可将状态改为“已确认”。
3. 使用 `$speckit-plan` 将已确认需求映射到当前工程事实。用户必须单独确认 `plan.md`，
   方案确认不得被推断为实现授权。
4. 使用 `$speckit-tasks` 生成可执行任务。用户必须单独确认 `tasks.md` 的范围、顺序和验证方式。
5. 使用 `$speckit-analyze` 做非破坏性一致性检查。所有 CRITICAL 和 HIGH 问题必须解决或由用户
   明确接受；随后仍须获得用户在当前任务中明确的实施授权，才能运行 `$speckit-implement`。
6. 实施后按 `AC-xxx` 验证并记录证据；若实现与工件仍不收敛，使用 `$speckit-converge`
   补齐真实剩余任务，不得静默扩大范围。Converge 新增任何任务时必须将 Tasks 恢复为草稿，
   重新经过 Tasks 确认、Analyze 和明确实施授权，不能沿用旧确认直接继续实现。

本文中的“人工确认”必须来自当前任务中的真实人员：Spec 由需求负责人确认，Plan 由用户或
用户明确指定的技术评审人确认，Tasks 由用户或明确指定的实施评审人确认。CRITICAL/HIGH
风险只能由用户或用户明确授权且对该风险负责的人接受。AI、自动 workflow、工件生成者和
未被明确授权的旁观评审都不能自我确认，也不能推断授权关系。

任何内置或自定义的一键 workflow 都不得合并、跳过或自动推断上述人工门禁。并行需求必须
隔离各自的 Feature 目录和工作区，禁止依赖机器本地的“当前 Feature”指针误改另一项需求。

## Authority Index

发生冲突时，按以下顺序定位依据并显式报告冲突，而不是自行拼接结论：

1. 当前用户的直接指令与用户已确认的 `spec.md` 决定业务意图；新指令改变需求时必须更新并
   重新确认 Spec。
2. 真实 Controller、VO、POM、配置、SQL、迁移和源代码决定当前实现事实。
3. `CLAUDE.md` 决定稳定工程边界、契约规则和编码约束；`AGENTS.md` 是快速入口。
4. `docs/AI-设计系统上下文.md`、设计 Token 和相应平台适配文档决定 UI 与交互实现。
5. `docs/工程版本基线.md` 决定版本治理，`docs/工程现状.md` 决定当前完成度和业务留白。

文档与真实代码不一致时，必须先核实变更历史和运行结果；不得选择更方便的一方继续实现。

## Governance

本宪章约束本仓库所有 Spec Kit 工件、AI 会话和人工开发流程，并高于便捷性建议和自动化默认值。
修改宪章必须由用户明确授权，在同一变更中说明影响的原则、模板和迁移方式。版本遵循语义化：
删除或重新定义门禁为 MAJOR，新增原则或实质扩展治理为 MINOR，澄清且不改变含义为 PATCH。

每次需求审查、计划审查、任务审查和代码交付都必须检查本宪章。无法满足时必须停止在对应
门禁前，记录偏离、原因、影响和用户决定；不得先实现后补理由。
